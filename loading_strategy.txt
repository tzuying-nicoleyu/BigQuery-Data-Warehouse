NETSUITE -> BIGQUERY LOADING STRATEGY
======================================
Project: clean-pilot-456915-t0   Dataset: NetSuite
Source: pull_data_by_sql(query=q, return_df=True) (extract_from_netsuite module, auth already handled)

GENERAL CONVENTIONS (apply to every table unless noted otherwise)
-------------------------------------------------------------------
- Every table gets a "_loaded_at" TIMESTAMP (UTC) column, stamped at load time, to track load freshness
  separately from NetSuite's own lastmodifieddate.
- NetSuite booleans come back as "T"/"F" strings -> mapped to Python True/False.
- Column names in the response are ALWAYS lowercased, regardless of how they're cased in the SELECT
  (e.g. "autoLeadTime" comes back as "autoleadtime"). Cast/schema code must reference the lowercase form.
- Joinable/reference fields (parent, class, mainaddress, purchaseunit, etc.) return the raw internal ID,
  not the name, unless wrapped in BUILTIN.DF(...) or explicitly joined.
- "subsidiary" can be a multi-value comma-separated string of IDs (e.g. "2, 5, 32") - kept as STRING,
  not modeled as a clean FK.
- lastmodifieddate (and similar NetSuite date fields) are date-only strings (M/D/YYYY) -> cast to
  BigQuery DATE (via .dt.date), not TIMESTAMP, to avoid implying false time precision.
- Avoid BigQuery NUMERIC for cost/price columns loaded via load_table_from_dataframe - repeatedly hit
  pyarrow errors (byte-length mismatch, then "rescaling would cause data loss"). Use FLOAT instead
  unless a specific downstream need requires exact decimal precision.
- pyarrow must be installed in the same .venv as the notebook kernel, and the kernel must be restarted
  after installing it (google-cloud-bigquery caches a module-level pyarrow-is-None check at import time).
- NetSuite SuiteQL "OFFSET n ROWS FETCH NEXT m ROWS ONLY" pagination is NOT safe for deep pagination on
  large tables: past some internal offset ceiling (confirmed well under 1.265M on this account, exact
  threshold unknown), NetSuite silently WRAPS AROUND and re-returns rows from the beginning instead of
  returning fewer/no rows. It does not error - it just quietly repeats data, so a naive loop that stops
  on "empty result" or "fewer rows than requested" will never terminate and will re-pull duplicate data
  forever. Use KEYSET (cursor) pagination instead for any large table: "WHERE id > :last_seen_id ORDER
  BY id FETCH NEXT n ROWS ONLY", tracking last_seen_id as the max id of the previous page. This never
  asks for a deep offset, so it never hits the wraparound ceiling, regardless of table depth.
- Reminder: "id" (and similar fields) come back from NetSuite as STRINGS, not numbers. Do not use
  pandas .is_monotonic_increasing / sort comparisons directly on these columns - "10000" < "9999"
  lexicographically even though 10000 > 9999 numerically. Cast to a numeric dtype first.

    (e.g. journal entries). Confirmed transaction.entity joins directly to customer.id for
    salesorder-type transactions; for other transaction types it may point to a vendor/other

  - employee: integer, nullable. Reference to an employee record - no employee table loaded in
    this pipeline yet, so this stays an unjoined ID for now.

STRATEGY - three separate pieces:

1) ONE-TIME HISTORICAL BACKFILL (backfill_transaction() function)
   - Paginate from NetSuite via KEYSET pagination: "WHERE id > :last_id ORDER BY id FETCH NEXT
     <chunk_size> ROWS ONLY" (chunk_size=5000), tracking last_id = max(id) of the previous page
     (cast to int64 first - id comes back as a string). Loop until a page returns fewer rows than
     chunk_size, or an empty page.
   - Originally implemented with "OFFSET n ROWS FETCH NEXT ... ROWS ONLY" instead - switched away
     from this after discovering NetSuite silently wraps OFFSET around past some internal ceiling
     (see general conventions above) which caused the backfill to loop indefinitely re-pulling
     duplicate data from the beginning of the table without ever detecting completion.
   - Accumulate ALL pages into one combined DataFrame (pd.concat) - do NOT load each page to
     BigQuery separately. Do ONE single load_table_from_dataframe call for the whole backfill.
     Reason: hit BigQuery's "partition modifications per column-partitioned table per day" quota
     (documented ~5,000/day) when doing per-chunk loads, because id-ordered chunks scatter across
     many different date partitions - each small load job touched a huge number of partitions,
     and the cumulative count across ~253 jobs blew past the quota almost immediately.
   - write_disposition = WRITE_TRUNCATE (explicit, not left blank - blank defaults to WRITE_EMPTY
     which errors if the table already has any rows from a prior partial/failed attempt).
     create_disposition = CREATE_IF_NEEDED.
   - Table partitioned by trandate at MONTH granularity (not DAY) - switched from DAY after hitting
     the quota error; MONTH gives ~96 partitions over 8 years vs ~2,920 for DAY, while still giving
     meaningful query-pruning benefit for typical month/quarter sales-analysis queries (year would be
     too coarse for that).
   - Clustered by recordtype.
   - IMPORTANT: partitioning cannot be changed on an existing table. Since an earlier failed run
     (old code, DAY partitioning, per-chunk loads) already created/partially loaded the transaction
     table (~215-220K rows) before hitting the quota wall, the existing table MUST be deleted
     (client.delete_table(TABLE_REF, not_found_ok=True)) before rerunning the fixed backfill function,
     otherwise the new MONTH partitioning config will be ignored/conflict.

2) ONGOING REGULAR REFRESH (NOT YET BUILT)
   - Decided against pure lastmodifieddate-watermark incremental. Instead: a rolling 2-year window
     re-pull, based on real data evidence (rows with lastmodifieddate in 2026, grouped by trandate
     year): 99.46% of edit activity touches transactions dated within the last 2 years (2025+2026);
     the tail beyond 2 years is real but small (~0.5%, going back as far as 2017).
   - Every regular run: re-pull the FULL current state of everything with
     trandate >= (today - 2 years), stage it, then MERGE into the target table:
       - WHEN MATCHED -> UPDATE (catches edits)
       - WHEN NOT MATCHED BY SOURCE AND target.trandate >= cutoff_date -> DELETE (catches real
         deletions within the window - the "AND target.trandate >= cutoff_date" guard is critical,
         otherwise this would delete all pre-window history too)
       - WHEN NOT MATCHED -> INSERT (catches new transactions)
   - This bounds partition touches to a fixed recent window every run (quota-safe, unlike the
     original id-ordered full-history approach), and self-heals both edits and deletes without
     needing separate delete-reconciliation logic or watermark state tracking.
   - Mechanically: load the pulled window into a staging table (WRITE_TRUNCATE, disposable), then
     run the MERGE as a client.query(...) SQL job - NOT achievable via load_table_from_dataframe's
     write_disposition parameter alone (no MERGE option there).
   - No watermark control table needed for this approach (the "today - 2 years" cutoff is computed
     fresh each run, no state to persist). The earlier lastmodifieddate-watermark design (Option A:
     derive from MAX(lastmodifieddate) in the target table) was superseded by this rolling-window
     design and is not needed unless the strategy changes back.

3) QUARTERLY FULL RECONCILIATION (NOT YET BUILT, but no new code needed)
   - Catches the small (~0.5%) long tail of edits to transactions older than the 2-year rolling
     window, which (1) never gets touched otherwise.
   - Just re-run backfill_transaction() itself (full pull, WRITE_TRUNCATE) on a quarterly cadence.
     Safe quota-wise because it's a single load job, run infrequently (quarterly, not daily).
   - Chosen over a full-history MERGE-with-delete because it's simpler and already-written, and at
     quarterly frequency the quota risk is negligible.

TABLE: transactionline
-------------------------------------------------------------------
Status: REFRESH CODE COMPLETE, tested and running.
Scale: ~2.6M rows in refresh window (linecreateddate >= cutoff), ~5K rows in edit tail.
       Full table is larger; only the rolling 2-year window is re-pulled each run.

Strategy: Two-pass stage + MERGE. Cannot use a single lastmodifieddate filter because rows
          created before the cutoff that were never edited since would disappear from staging
          and be deleted by the MERGE DELETE guard. Two passes capture the full window correctly.

Rolling window cutoff:
  cutoff = date.today() - timedelta(days=365 * 2)   # 2-year rolling window

PASS 1 — 2 years window lines (linecreateddate >= cutoff)
  Volume: ~2.6M rows — dense data, many rows per key slice.
  Filter: WHERE linecreateddate >= '{cutoff}'
            AND uniquekey >  {s_start}
            AND uniquekey <= {s_end}
          ORDER BY uniquekey
  The upper bound (uniquekey <= s_end) is mandatory. Without it, NetSuite scans from s_start
  to end of table (O(table)). With it, NetSuite uses an index range scan (O(slice)).
  Same two-sided bound strategy as load_year() in bigquery.ipynb.
  Execution: 3 concurrent worker threads drain a shared queue.Queue of 100K-key slices.
             MIN/MAX uniquekey queried first to build the slice list.
             Each worker owns its own bigquery.Client (avoids thread contention).
             Failed slices requeued from last successfully flushed key (up to 3 retries).
             flush_every=10 (50K rows per flush) to stay under BigQuery load job rate limits.
  Pass 1 CLEARS the staging table before starting (WRITE_TRUNCATE first load, WRITE_APPEND after).

PASS 2 — Edited old lines (linelastmodifieddate >= cutoff AND linecreateddate < cutoff)
  Volume: ~5K rows — sparse data, only 2-3 rows per 100K-key slice.
  Filter: WHERE linelastmodifieddate >= '{cutoff}'
            AND linecreateddate < '{cutoff}'
            AND uniquekey > {last_key}
          ORDER BY uniquekey
  Cannot use slice approach here: each 100K-key slice yields 2-3 rows, producing hundreds of
  tiny BigQuery load jobs which immediately hit 429 TooManyRequests rate limits.
  Execution: serial keyset loop, accumulates ALL pages into a buffer, single WRITE_APPEND
             load job at the end. Total ~5K rows fits comfortably in memory.
  Pass 2 APPENDS to staging (does not clear it — Pass 1 data must be preserved).

BigQuery 429 rate limit handling (both passes):
  _flush_tl_batch catches TooManyRequests and retries with exponential backoff:
  wait = 15s × 2^attempt  (15s, 30s, 60s, 120s, 240s, then raise on 6th failure)
  flush_every=10 reduces total concurrent load jobs across the 3 workers.

MERGE (merge_transactionline):
  Runs after both passes complete. Uses a deduplication subquery in the USING clause
  because a row with both linecreateddate >= cutoff AND linelastmodifieddate >= cutoff
  appears in both Pass 1 and Pass 2, causing duplicate uniquekeys in staging.
  BigQuery raises "UPDATE/MERGE must match at most one source row" without dedup.

  MERGE `transactionline` AS T
  USING (
      SELECT * EXCEPT (rn)
      FROM (
          SELECT *, ROW_NUMBER() OVER (PARTITION BY uniquekey ORDER BY _loaded_at DESC) AS rn
          FROM `transactionline_staging`
      )
      WHERE rn = 1
  ) AS S
  ON T.uniquekey = S.uniquekey
  WHEN MATCHED THEN UPDATE SET <all columns>
  WHEN NOT MATCHED BY TARGET THEN INSERT <all columns>
  WHEN NOT MATCHED BY SOURCE
       AND T.linecreateddate >= DATE '{cutoff}' THEN DELETE

  DELETE guard: only rows where linecreateddate >= cutoff are eligible for deletion.
  Rows created before the cutoff that were deleted in NetSuite are NOT caught — accepted
  limitation, same as transaction table refresh.

  WARNING: if staging is incomplete (either pass failed partway), the DELETE guard will
  remove target rows that are missing from staging. Always verify staged row count before
  running merge_transactionline().

Functions in refresh.py (callable independently for testing):
  stage_transactionline_pass1()   # dense, concurrent workers, clears staging
  stage_transactionline_pass2()   # sparse, serial accumulate-all, appends to staging
  merge_transactionline()         # deduplicated MERGE — verify staging first
  refresh_transactionline()       # orchestrator: pass1 -> pass2 -> merge

Columns: uniquekey, id, transaction, item, itemtype, quantity, rate, netamount, foreignamount,
         linesequencenumber, mainline, fulfillable, location, subsidiary, entity, shipmethod,
         createdfrom, linecreateddate, linelastmodifieddate, quantitycommitted,

         isfullyshipped, closedate, duedate, expectedshipdate, actualshipdate, _loaded_at
