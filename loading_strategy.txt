Project: clean-pilot-456915-t0   Dataset: NetSuite

GENERAL CONVENTIONS (apply to every table unless noted otherwise)
-------------------------------------------------------------------
- Every table gets a "_loaded_at" TIMESTAMP (UTC) column, stamped at load time, to track load freshness
  separately from NetSuite's own lastmodifieddate.
- NetSuite booleans come back as "T"/"F" strings -> mapped to Python True/False.
- Column names in the response are ALWAYS lowercased, regardless of how they're cased in the SELECT
  (e.g. "autoLeadTime" comes back as "autoleadtime"). Cast/schema code must reference the lowercase form.
- Joinable/reference fields (parent, class, mainaddress, purchaseunit, etc.) return the raw internal ID,
  not the name, unless wrapped in BUILTIN.DF(...) or explicitly joined.
- "subsidiary" can be a multi-value comma-separated string of IDs (e.g. "2, 5, 32") - kept as STRING,
  not modeled as a clean FK.
- lastmodifieddate (and similar NetSuite date fields) are date-only strings (M/D/YYYY) -> cast to
  BigQuery DATE (via .dt.date), not TIMESTAMP, to avoid implying false time precision.
- Avoid BigQuery NUMERIC for cost/price columns loaded via load_table_from_dataframe - repeatedly hit
  pyarrow errors (byte-length mismatch, then "rescaling would cause data loss"). Use FLOAT instead
  unless a specific downstream need requires exact decimal precision.
- pyarrow must be installed in the same .venv as the notebook kernel, and the kernel must be restarted
  after installing it (google-cloud-bigquery caches a module-level pyarrow-is-None check at import time).
- NetSuite SuiteQL "OFFSET n ROWS FETCH NEXT m ROWS ONLY" pagination is NOT safe for deep pagination on
  large tables: past some internal offset ceiling (confirmed well under 1.265M on this account, exact
  threshold unknown), NetSuite silently WRAPS AROUND and re-returns rows from the beginning instead of
  returning fewer/no rows. It does not error - it just quietly repeats data, so a naive loop that stops
  on "empty result" or "fewer rows than requested" will never terminate and will re-pull duplicate data
  forever. Use KEYSET (cursor) pagination instead for any large table: "WHERE id > :last_seen_id ORDER
  BY id FETCH NEXT n ROWS ONLY", tracking last_seen_id as the max id of the previous page. This never
  asks for a deep offset, so it never hits the wraparound ceiling, regardless of table depth.
- Reminder: "id" (and similar fields) come back from NetSuite as STRINGS, not numbers. Do not use
  pandas .is_monotonic_increasing / sort comparisons directly on these columns - "10000" < "9999"
  lexicographically even though 10000 > 9999 numerically. Cast to a numeric dtype first.

STRATEGY:

1) ONGOING DAILY REFRESH (refresh_transaction() in refresh.py)
   Rolling 2-year window MERGE refresh. Every run:
   a. Pull all transactions WHERE trandate >= today - 2 years (keyset pagination, chunk_size=5000)
   b. Load into transaction_staging (WRITE_TRUNCATE)
   c. MERGE staging -> target:
      - WHEN MATCHED -> UPDATE (catches edits)
      - WHEN NOT MATCHED BY TARGET -> INSERT (catches new transactions)
      - WHEN NOT MATCHED BY SOURCE AND T.trandate >= cutoff -> DELETE (guarded, window only)
   Partitioned by trandate (MONTH granularity), clustered by type.

2) FULL HISTORICAL BACKFILL / DISASTER RECOVERY (backfill_transaction() in backfill.py)
   Full WRITE_TRUNCATE load of all transactions, single load job to avoid partition quota issues.
   Run manually: python backfill.py --job backfill_transaction
   Use for: initial load, disaster recovery, or quarterly full reconciliation of the
   ~0.5% long tail of edits to transactions older than the 2-year rolling window.

STRATEGY — three separate pieces:

1) DAILY REFRESH (refresh_transactionline(full=False) in refresh.py)
   Pass 1 + MERGE only. Catches all new rows created within the rolling 2-year window.
   Command: python refresh.py --job transactionline
   Schedule: daily 02:00 UTC (after transaction refresh completes)

2) MONTHLY FULL REFRESH (refresh_transactionline(full=True) in refresh.py)
   Pass 1 + Pass 2 + MERGE. Catches new rows AND old rows edited within the window.
   Command: python refresh.py --job transactionline_full
   Schedule: 1st of every month 02:00 UTC

   PASS 1 — New lines (linecreateddate >= cutoff) — ~2.6M rows, DENSE
     Filter: WHERE linecreateddate >= '{cutoff}'
               AND uniquekey >  {s_start}
               AND uniquekey <= {s_end}
             ORDER BY uniquekey
     Upper bound (uniquekey <= s_end) is mandatory — makes NetSuite use O(slice) index range
     scan instead of O(table) full scan.
     Execution: 3 concurrent workers drain a shared queue.Queue of 100K-key slices.
                MIN/MAX uniquekey pre-fetched to scope the slice list.
                Failed slices requeued from last successfully flushed key (up to 3 retries).
     Pass 1 CLEARS staging before starting.

   PASS 2 — Edited old lines (linelastmodifieddate >= cutoff AND linecreateddate < cutoff) — ~19K rows, SPARSE
     Filter: WHERE linelastmodifieddate >= '{cutoff}'
               AND linecreateddate < '{cutoff}'
               AND uniquekey > {last_key}
             ORDER BY uniquekey
     IMPORTANT: Do NOT use bounded-slice concurrency here. The uniquekey range spans ~13M keys
     for only ~19K rows (~2 rows per 100K-key slice). Concurrent slices produce hundreds of
     tiny BigQuery load jobs and trigger 429 rate limits immediately.
     Execution: serial keyset loop, all pages accumulated in memory, single WRITE_APPEND at end.
                ~4 API calls total at chunk_size=5000. Slower per-call (~35s/call) due to
                two-condition WHERE clause; accepted as a monthly-only cost.
     Pass 2 APPENDS to staging (does not clear it).

   MERGE (merge_transactionline):
     Deduplication subquery required — a row with both linecreateddate >= cutoff AND
     linelastmodifieddate >= cutoff appears in both passes, causing BigQuery
     "MERGE must match at most one source row" error without it.
     DELETE guard: only rows where linecreateddate >= cutoff are eligible for deletion.
     WARNING: verify staged row count before running merge — incomplete staging + DELETE
     guard = data loss.

3) FULL HISTORICAL BACKFILL / DISASTER RECOVERY (backfill_transactionline() in backfill.py)
   Drops and recreates table, then loads year by year (WRITE_APPEND after first year).
   Each year uses concurrent bounded-slice workers (same as Pass 1).
   Verifies BigQuery row count vs NetSuite count after each year.
   Historical row counts (as of Sept 2026):
     2018:  182K | 2019:  833K | 2020: 1.01M | 2021:  907K
     2022:  864K | 2023:  948K | 2024: 1.06M | 2025: 1.14M | 2026: 972K
     Total: ~7.9M rows
   Commands:
     python backfill.py --job backfill_transactionline           # all years
     python backfill.py --job backfill_transactionline --years 2025 2026  # specific years
